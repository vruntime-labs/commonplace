# Contributing to Commonplace

Thank you for your interest in improving Commonplace.

Commonplace is an open knowledge project. Contributions can improve the software, documentation, learning material, resource records, accessibility, security, and the way the community works together.

You do not need to be an experienced developer to contribute. Clear corrections, useful sources, careful reviews, and beginner-friendly explanations are valuable.

## Ways to contribute

- Correct or improve documentation.
- Write or improve a learning guide, tutorial, reference, or checklist.
- Suggest a useful developer resource.
- Report inaccurate, outdated, broken, or unsafe information.
- Improve accessibility, performance, tests, or project tooling.
- Review open issues and pull requests.
- Share constructive feedback about the product.

## GitHub contribution process

The current contribution path is GitHub-first:

1. Check existing issues and pull requests to avoid duplicate work.
2. Open an issue for substantial changes or discuss the proposal with maintainers.
3. Fork the repository.
4. Create a focused branch for your change.
5. Make the change and check formatting, links, and accuracy.
6. Submit a pull request against the `main` branch.
7. Respond to review feedback and update the pull request where needed.

Keep pull requests focused. Smaller changes are easier to review and maintain.

## Content and resource standards

Contributions should be:

- Accurate, useful, and relevant to people who build with technology.
- Clear about the intended audience, prerequisites, and limitations.
- Supported by reliable sources where factual or technical claims need evidence.
- Honest about uncertainty, compatibility, version requirements, and maintenance status.
- Properly attributed and compatible with applicable licences.
- Written in clear language without unnecessary promotion or unsupported claims.

When proposing a third-party resource, include as much relevant information as possible:

- Resource name and purpose.
- Official source or project repository.
- Licence or reuse terms, when known.
- Supported versions, platforms, and compatibility.
- Installation or usage documentation.
- Maintenance status and known limitations.
- Relevant permissions, security considerations, or risks.

Do not present an unverified resource as officially endorsed or security-audited by Commonplace.

For detailed content requirements, review the [content model](docs/content/content-model.md), [editorial policy](docs/governance/editorial-policy.md), and [contribution guidelines](docs/governance/contribution-guidelines.md).

## Security and privacy

Never include passwords, API keys, access tokens, private user data, or other secrets in issues, pull requests, commits, screenshots, or documentation.

Do not submit malicious code, harmful instructions, or content that knowingly compromises users or systems. If you discover a security vulnerability, follow [SECURITY.md](SECURITY.md) rather than reporting exploitable details publicly.

## Pull request expectations

A useful pull request should:

- Explain what changed and why.
- Identify related issues or discussions, if any.
- Keep unrelated changes out of scope.
- Include relevant tests or verification notes for code changes.
- Include screenshots for meaningful interface changes.
- Credit sources and authors where required.
- Disclose known limitations or incomplete work.

Before submitting, check that:

- [ ] The change has a clear purpose.
- [ ] Existing content and functionality have not been unintentionally removed.
- [ ] Links and references work.
- [ ] Claims are accurate and appropriately sourced.
- [ ] Third-party content is attributed and its reuse terms are respected.
- [ ] No secrets or private data are included.

## Website-based contributions

A guided website-based submission path is an approved MVP requirement, but it is not available yet. Until it launches, use GitHub issues for suggestions and pull requests for proposed changes.

When introduced, website submissions will enter the same review and publication process as GitHub contributions. The submission flow must not expose a privileged GitHub write token or other secrets in browser code. See the detailed [contribution guidelines](docs/governance/contribution-guidelines.md).

## Licensing and ownership

The repository's source-code licence is still under consideration. A publicly accessible repository is not automatically permission to copy, redistribute, or relicense its contents.

Only submit work that you created or are authorised to contribute. Identify third-party material and its licence clearly. Do not assume that content found online is free to reproduce.

The project will publish its licensing and contribution terms when those decisions are made. Until then, ask maintainers if you are unsure whether a proposed contribution can be accepted.

## Review process

Maintainers may request clarification, changes, sources, attribution, or evidence. Contributions are reviewed for relevance, quality, accuracy, safety, accessibility, maintainability, and licensing concerns.

Submitting a contribution does not guarantee that it will be accepted or merged. Maintainers may decline or defer changes that do not fit the project's direction or standards.

## Community standards

All contributors are expected to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

Thank you for helping keep useful knowledge available to everyone.
